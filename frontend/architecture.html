01

دامنه‌ی MVP

دموی تعاملیِ فعلی (جست‌وجوی ملک، چت مشاور، محاسبه‌گر بودجه) با داده‌ی نمونه ساخته شده تا مفهوم را نشان دهد. هدف این سند، مشخص کردن چیزی‌ست که برای تبدیل آن به یک محصول واقعی — با داده‌ی زنده‌ی DLD و پاسخ‌های هوش مصنوعیِ واقعی — لازم است.

مرز MVP واقعی (فاز اول، Q1–Q2)

جست‌وجو و ارزیابی قیمت برای شهر دبی به‌تنهایی (نه کل امارات)، مشاور ویزا فقط برای سه مسیر پرتکرار (اقامت ملکی، ویزای طلاییِ ملکی، ویزای طلاییِ کارآفرینی)، و همتایابی سبک زندگی با حداکثر ۶ فیلتر ثابت. اپ موبایل، پشتیبانی چندزبانه و کانسیرژ پرمیوم به فازهای بعدی موکول می‌شود.

02

معماری سیستم

کلاینت از طریق یک API Gateway به سه سرویس اصلی می‌رسد؛ هر سرویس یا از پایگاه‌داده‌ی مشترک می‌خواند/می‌نویسد یا برای استدلال زبانی به Claude API متکی است. داده‌ی خام قیمت از یک خط لولهٔ ETL روزانه از Dubai Pulse تغذیه می‌شود.

04

مدل داده

شمای اصلی PostgreSQL — فقط جدول‌های هسته‌ای MVP، بدون جزئیات ستون‌های ثانویه.

properties        id, area, type, bedrooms, size_sqft, developer_id, geo_point
transactions      id, property_id, price_aed, date, source ('DLD' | 'listing')
valuations        property_id, predicted_price_aed, confidence, model_version, computed_at
visa_rules        id, route ('property_2y' | 'golden_property' | 'golden_entrepreneur'),
                   min_investment_aed, duration_years, requires_sponsor, updated_at
visa_sessions     id, user_id, budget_aed, goal, recommended_route_id, created_at
agencies          id, name, tier ('pilot' | 'paid'), contact
leads             id, agency_id, property_id, user_id, status, created_at
05

مدل‌های هوش مصنوعی

چهار قابلیت هوش مصنوعیِ پیچ‌دک، در MVP به سه مدل/سرویس فنی نگاشت می‌شود (مشاور ویزا و دستیار اسناد یک سرویس مشترک‌اند چون هر دو روی استدلال زبانی متکی‌اند).

مدل ارزیابی قیمت

gradient-boosted regression (LightGBM)

ورودی: منطقه، متراژ، نوع ملک، طبقه، سن ساختمان. آموزش روی تاریخچه‌ی تراکنش‌های DLD. خروجی: قیمت پیش‌بینی‌شده + بازه‌ی اطمینان، نه یک عدد قطعی.

داده: DLD historicalبازآموزی: هفتگیسنجه: MAE بر حسب AED

مشاور ویزا و اسناد

rules engine + Claude API (RAG)

آستانه‌های ویزا (مبلغ، مدت، نیاز به کفیل) به‌صورت جدول قانونمند نگه‌داری می‌شود — نه چیزی که مدل زبانی حدس بزند. Claude فقط برای گفت‌وگوی طبیعی، خلاصه‌سازی مدارک و توضیح ساده‌ی نتیجه به کار می‌رود؛ منبع حقیقتِ عددی همیشه جدول قوانین است.

منبع حقیقت: visa_rulesLLM: توضیح، نه تصمیمبازبینی انسانی: الزامی قبل از هر مشاوره‌ی نهایی

همتایاب سبک زندگی

embedding similarity (pgvector)

هر ملک بر اساس ویژگی‌های محله (فاصله تا مدرسه، ساحل، مترو، تراکم جامعه‌ی فارسی‌زبان) به یک بردار نگاشت می‌شود؛ جست‌وجو با نزدیک‌ترین‌همسایه به‌جای فیلتر سخت‌گیرانه انجام می‌شود.

ذخیره: pgvectorورودی اولیه: داده‌ی دستی محله‌ها (فاز ۱)

محدودیتِ عمدی

هیچ خروجی مدل ارزیابی یا مشاور ویزا به‌عنوان مشاوره‌ی قطعیِ مالی یا حقوقی نمایش داده نمی‌شود؛ هر پاسخ باید به همراه رد پای منبع (کدام تراکنش‌ها، کدام قانون) و دکمه‌ی «تأیید با مشاور مجاز» ارائه شود.

08

نقشه‌ی ساخت مرحله‌ای

Q1

پایه‌ی فنی

  • بک‌اند FastAPI + شمای PostgreSQL بالا
  • مدل ارزیابی نسخه‌ی اول، آموزش‌دیده روی نمونه‌ی دیتاست DLD
  • مشاور ویزا با جدول قوانین دستی (بدون LLM هنوز)
Q2

داده‌ی زنده + بتای بسته

  • خط لوله‌ی ETL روزانه از Dubai Pulse
  • اتصال Claude API برای گفت‌وگوی طبیعی و تحلیل سند
  • فید لیستینگ ۵۰ آژانس پایلوت (شروع با CSV دستی)
Q3

لانچ عمومی

  • اپ موبایل React Native
  • همتایاب سبک زندگی با embedding کامل
  • پشتیبانی عربی/روسی/هندی در دستیار
Q4

مقیاس منطقه‌ای

  • افزودن ابوظبی، دوحه، ریاض (نیاز به منبع داده‌ی مشابه DLD در هر بازار)
  • مدل ارزیابی جدا برای هر بازار (cold-start متفاوت)
09

ریسک‌های فنی

وابستگی به یک منبع داده

اگر دسترسی به Dubai Pulse محدود یا تغییر فرمت شود، مدل ارزیابی متوقف می‌شود. کاهش ریسک: کش کردن دیتاست خام + نسخه‌بندی schema.

خطای LLM در حوزه‌ی حقوقی

Claude نباید منبع نهاییِ آستانه‌ی ویزا باشد. کاهش ریسک: جدول قوانین جدا + بازبینی انسانی قبل از هر پاسخ قطعی.

Cold-start بازارهای جدید

مدل قیمت برای ابوظبی/دوحه/ریاض بدون تاریخچه‌ی تراکنش دقیق نیست. کاهش ریسک: شروع با بازه‌ی اطمینان وسیع‌تر و برچسب «داده‌ی محدود».
